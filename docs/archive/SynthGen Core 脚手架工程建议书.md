一、核心观点：暗线不修，明线必断
路线图 v1.2 是一条明线——每个版本交付什么产品能力，组件清单、依赖链、验收标准都清晰。

但支撑这四个版本能被开发出来的，是一条暗线——脚手架工程。

什么是脚手架工程？它不是最终产品的一部分。它是建造产品所需的工具、设施和保障体系。没有脚手架，12层楼的进度表只是纸上谈兵——前3层还能靠爬梯子上去，第4层开始就需要脚手架了。

这条暗线如果不在路线图中显式规划，会导致：

组件间的协议接口被错误实现，到集成测试阶段才暴露（组件 #4 以为组件 #5 传过来的是行式，组件 #5 传的是列式）

执行路由器路径错误不可复现（只说了"走错了"，不知道哪一步走错了）

约束引擎的过滤逻辑无法被验证（没有 trace，无法逐条确认约束卡片的执行结果）

EvidencePackage 字段来源不可追溯（provenance 声明了数据来源，但构建过程的每一步没有记录）

脚手架工程的本质是：让不可见的东西可见。

二、脚手架工程清单
2.1 Explain 设施（执行计划可解释）
定义：用户可以请求系统解释一个生成请求的完整执行计划，而不实际执行生成。

类比：数据库的 EXPLAIN 命令——PostgreSQL 的 EXPLAIN SELECT ...，MySQL 的 EXPLAIN FORMAT=TREE。

对 SynthGen Core 的意义：

能力	说明	示例
生成计划预览	用户发出请求前，先看到系统会选择哪条路径	client.explain("sensor_log", constraints=["wind_safety"])
约束分类结果	哪些约束被识别为值域、哪些是行间、哪些是聚合	constraint_classification: {value_range: 2, inter_row: 1, aggregate: 1}
执行模式	系统选择了 row_by_row / stateful_batch / two_phase	execution_mode: two_phase
路由决策	选择了哪条退化路径，为什么	path: constrained_fusion, reason: constraints_complete AND data_sufficient
排除率预估	预估的排除率，是否触发了保守偏向	exclusion_rate_estimate: 0.45, conservative_bias: false
数据来源	会用哪个版本的训练数据、哪个版本的模型	model_version: gen_model_v2, training_data_range: ...
路线图建议：

v1 实现最小 explain：约束分类结果 + 执行模式 + 路由决策（插入在 #8 EvidencePackage 构建器中，作为生成请求的可选预查）

v2 增强：排除率预估 + 体积比计算细节 + 数据来源

v3 增强：compaction 影响预估（如果请求的版本已被 compaction，explain 会显示将退化的版本和偏差报告）

2.2 Trace 设施（执行过程可追踪）
定义：实际执行生成请求时，系统记录执行路径上的每一步操作，并赋予全局唯一的 trace_id。用户事后可按 trace_id 查询完整操作链。

类比：分布式系统的分布式追踪——OpenTelemetry span、Jaeger trace。

对 SynthGen Core 的意义：

能力	说明
每个生成请求产生唯一 trace_id	evp_20260510_a3f2b8c1 同时是 package_id 和 trace_id
操作步骤按 span 记录	LOAD DATA → CONSTRAINTS_LOADED → CONSTRAINT_CLASSIFICATION → GENERATION_START → PHYSICS_SAMPLE_BATCH_1 → VALUE_FILTER_PASS_85 → INTER_ROW_FILTER_PASS_72 → AGGREGATION_WINDOW_1 → EVIDENCE_BUILD → COMPLETE
每步记录耗时和状态	span: INTER_ROW_FILTER_BATCH_3, duration_ms: 42, status: ok, rows_in: 128, rows_out: 104, violations: 24
每步记录操作者身份	actor: {component: "constraint_engine", caller_id: "exec_router"}
错误定位	如果某步失败，trace 指向失败位置、输入和错误原因
路线图建议：

v1 实现最小 trace：每个组件产生 span，写入 EvidencePackage 的 provenance 中。trace_id = package_id。

v2 增强：后筛选路径的 trace 额外记录体积比计算和排除率实时变化。

v3 增强：持续对齐的 trace 额外记录模型更新前后的分布变化。

2.3 系统可观测性
定义：系统向外暴露内部状态，供监控和诊断。不是事后查 trace，而是实时看指标。

类比：Prometheus metrics / Grafana dashboard。

对 SynthGen Core 的意义：

能力	说明
生成吞吐量和延迟	每秒生成行数、请求完成时间分布
排除率实时趋势	当前活跃请求的排除率变化曲线
引擎负载	物理引擎占用率、数据引擎占用率、存储 I/O
内存占用	模型常驻内存、生成 batch 缓冲区、frame buffer
退化路径命中率	各条退化路径的请求比例和切换频率
数据引擎状态	KDE 模型状态、训练数据量、维度数
审计日志大小和验证状态	审计链长度、最近验证时间、验证结果
路线图建议：

v1 实现最小可观测性：生成吞吐量 + 请求完成延迟 + 内存占用（作为进程内 metrics 端点）

v2 增强：排除率实时趋势 + 退化路径命中率 + 审计验证状态

v3 增强：模型版本链状态 + GC compaction 历史

2.4 确定性测试框架
定义：给定确定的输入（seed + 约束卡片 + 训练数据快照 + 生成器版本），输出必然一致。这个框架验证这个承诺。

类比：数据库的回归测试套件——PostgreSQL 的 make check。

对 SynthGen Core 的意义：

能力	说明
Seed 固定	每个生成请求指定 seed，复现时可完全重现
参考输出快照	v1/v2/v3 每个版本发布时，生成一份参考输出快照。后续任何代码改动必须能重现完全一致的输出
关键路径回归测试	5条退化路径，每条路径有固定的测试用例和预期输出
EvidencePackage 模式验证	自动验证产出的 EvidencePackage 是否符合 Schema v1.2
约束卡片全集测试	一组标准约束卡片（值域+行间+聚合），每次代码变动后自动跑全量
路线图建议：

v1 实现最小测试框架：seed 固定 + 参考输出快照 + EvidencePackage Schema 自动验证

v2 增强：5条退化路径各一个回归测试用例

v3 增强：compaction 影响测试（compaction 前后生成结果的一致性验证）

2.5 回归测试基础设施
定义：自动化的持续集成环境，每次代码提交自动触发全套测试。

类比：CI/CD pipeline——GitHub Actions、Jenkins。

对 SynthGen Core 的意义：

能力	说明
代码提交触发	每次 PR 自动运行 Parser 单元测试 + 引擎集成测试 + 端到端生成测试
标准测试数据集	一组固定的小型 Parquet 文件（如 1000 行传感器数据），所有测试基于此
预期输出比对	测试的输出与参考快照逐行比对，不一致则报 regression
EvidencePackage 完整性检查	自动调用 Schema 验证器，确认必选字段齐全
性能回归	每次提交记录生成吞吐量，超出基线±10% 报警
路线图建议：

v1 建立 CI 基础设施 + 标准测试数据集 + 参考输出快照

每个后续版本新增功能时，同步新增对应的回归测试用例

2.6 错误注入与退化路径验证
定义：人为制造故障场景，验证退化路径是否按预期触发。

类比：混沌工程——Netflix Chaos Monkey。

对 SynthGen Core 的意义：

能力	说明
约束卡片不完整注入	故意移除部分约束卡片，验证系统是否降级为统计生成
数据引擎故障注入	让数据引擎返回错误，验证系统是否回退纯物理
后筛选排除率模拟	注入极高排除率，验证系统是否拒绝后筛选路径
存储后端延迟注入	模拟对象存储高延迟，验证超时截断是否正确触发
路线图建议：

v2 引入：后筛选路径的排除率模拟 + 数据引擎故障注入

v3 引入：compaction 冲突场景注入

三、脚手架嵌入路线图的建议
3.1 作为并行工程
脚手架工程不应成为某个功能版本的一部分——它应与功能版本并行推进。每个功能版本交付时，对应的脚手架设施也必须就位。

脚手架项	v1	v2	v3	v4
Explain（最小：路由决策+约束分类）	✅	增强	—	—
Trace（最小：span结构+trace_id）	✅	增强	增强	—
可观测性（最小：吞吐量+延迟+内存）	✅	增强	增强	—
确定性测试框架（seed固定+参考快照）	✅	增强	增强	—
CI/CD + 回归测试基础设施	✅	—	—	—
错误注入（退化路径验证）	—	✅	✅	—
3.2 每个版本的验收标准增加脚手架项
v1 脚手架验收标准：

Explain 可显示约束分类结果 + 执行模式 + 路由决策（纯物理路径）

每个生成请求产生唯一 trace_id，span 记录到 EvidencePackage provenance

/metrics 端点可查询生成吞吐量、请求延迟、内存占用

固定 seed 产生的输出可与参考快照逐行比对

CI 环境就绪，每次 PR 触发 Parser 单元测试 + 端到端生成测试

v2 脚手架验收标准：

Explain 可显示排除率预估和体积比计算细节

Trace 可记录后筛选路径的实时排除率变化

可观测性增加排除率实时趋势和退化路径命中率

错误注入可模拟后筛选排除率爆炸，验证系统回退

5条退化路径各有一个回归测试用例

v3 脚手架验收标准：

Explain 可显示 compaction 影响预估

Trace 可记录持续对齐的模型更新前后变化

可观测性增加模型版本链状态和 GC 历史

错误注入可模拟 compaction 冲突

v4 脚手架验收标准：

Explain 可显示完备度评分对各路径的影响

Trace 可记录反例搜索的探索轨迹

3.3 脚手架工程的人员需求
脚手架工程不是"顺便做"的工作。Explain + Trace + 可观测性需要专人负责（可复用 Parser 开发者的抽象能力）。测试框架 + CI/CD 需要专人（可复用存储引擎开发者的基础设施能力）。

在 v1 的人员配置中，建议将"脚手架 & 基础设施"作为一条独立的并行线，由 1 人负责（可与 SDK 开发者复用，约 1.5 周工作量）。

四、脚手架工程的基本原则
4.1 与功能组件同版本交付
Explain 不是 v3 才需要的高级功能——v1 就需要。如果 v1 的一个生成请求，用户无法知道系统走了什么路径、为什么走这条路径、走了多久、每一步做了什么，用户就无法信任系统的输出。

4.2 脚手架代码也是生产代码
Trace span 的格式一旦定义，就不能随意改。Explain 的输出结构一旦定义，就成了隐式 API。脚手架不是"开发时用的临时工具，以后会删"——它是产品的一部分。

4.3 脚手架自身也需要可观测
Explain 的准确性谁来验证？Trace 的完整性谁检查？脚手架设施自身也需要测试和监控。Trace span 的丢失率应被可观测性系统监控。

4.4 最小可行脚手架
不要一开始就设计完整的 Explain 语法、完整的 Trace 系统、完整的 Grafana dashboard。从最小开始——就是那一个问题的答案：系统现在在做什么？

Explain：生成请求发出前，系统会走什么路径？

Trace：生成请求完成后，系统实际走了什么路径，每一步耗时多少？

可观测性：现在系统内存占用和吞吐量如何？

这三个问题的答案，是 v1 脚手架的最小可交付内容。

v1 最小可运行	Schema→导入→物理采样→值域验证→证据包	9	5（Explain/Trace/可观测性/测试框架/CI）	8-9周

六、一句话总结
明线交给路线图，暗线交给脚手架。明线决定产品能做什么，暗线决定团队能做到什么。

没有 Explain，团队不知道自己做的对不对。没有 Trace，出了错不知道从哪里查。没有可观测性，运行状态是盲人摸象。没有测试框架，每个版本都是一次豪赌。没有 CI，代码质量的底线全靠人肉。

这些不是"做完功能再做"的事情——它们是开发功能的前提。脚手架先搭好，砖才能往上垒。
