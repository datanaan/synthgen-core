SynthGen Core 工程框架 v0.2
—— AI原生数据库架构
一、为什么是数据库形态？
核心判断：SynthGen Core 的所有操作，本质上是对数据的变换、存储和检索。这不是类比，是严格对应。

SynthGen Core 操作	数据库对应操作	说明
接收用户输入数据	INSERT / BULK LOAD	数据进入系统
存储用户数据	表 / 分区	持久化
学习数据分布	CREATE MODEL（类似CREATE INDEX）	对数据建立衍生结构
生成新数据	SELECT ... WITH GENERATE	从模型查询数据
应用物理约束	WHERE 子句 / CHECK 约束	过滤和验证
版本管理	SNAPSHOT / TIME TRAVEL	时间点查询
审计追溯	WAL / 审计日志	不可变记录
结论：如果你做一个生成器，却从零开始写存储、查询、日志、权限系统，你就是在重复发明数据库。不如直接以数据库为骨架。

二、接口层：为什么是类SQL，而不是NoSQL？
2.1 接口选型分析
接口范式	代表	优势	对SynthGen Core的适配性
声明式查询（SQL）	PostgreSQL, DuckDB	Schema强约束，声明式语义，优化器成熟	✅ 天然契合：格式忠实性=Schema约束，物理约束=WHERE/CHECK，生成=查询
文档/键值（NoSQL）	MongoDB, Redis	Schema灵活，简单KV	❌ 灵活Schema与“输入格式忠实性”矛盾。无Schema意味着用户随时可以破坏维度基准
图查询	Neo4j, Cypher	关系建模	❌ 过度。数据生成的核心不是实体关系，是分布变换
编程API（SDK）	Python/C++ 库	灵活	✅ 做为底层存在，但不应是主要入口。API难以标准化，无法复用数据库生态
2.2 SQL 的关键适配理由
理由一：Schema是强制约束，不是建议。

SynthGen Core 的“输入格式忠实性”（理论框架4.1节）要求输出严格匹配输入的格式和维度。SQL的表Schema天然就是这种强约束——CREATE TABLE定义了列名、类型、约束，任何违反Schema的插入或查询直接报错。这恰好对应失败模式一（基准冲突）。

NoSQL的“灵活Schema”在这里是劣势：用户可以随时写入任意结构的数据，系统没有理论依据去拒绝。

理由二：物理约束映射为SQL约束，不需要新语言。

理论框架中的“约束卡片”（如风速∈[0,25]）可以直接映射为SQL CHECK约束或WHERE子句。不需要发明新的约束语言。

理由三：生成 = 查询，不是过程调用。

“生成一批满足某分布且在某物理边界内的数据”——这本质上是一个声明式查询，不是过程式编程。用户描述“要什么”，不是“怎么生成”。SQL的声明式语义恰好匹配。

理由四：生态复用最大化。

权限管理：GRANT/REVOKE 对应新数据来源边界（5.4节）和服务分级（7.2节）

日志审计：WAL 对应不可变审计追溯

时间旅行：SNAPSHOT 对应版本管理和代偿机制

存储优化：分区、索引、压缩 对应记忆策略

2.3 接口层的最终形态
对外暴露的不是一个“生成API”，而是一个支持扩展语法的SQL接口。

扩展点极少（仅GENERATE关键字），其余全部复用标准SQL。用户可以：

用标准SQL导入数据

用标准DDL定义约束卡片（表+CHECK约束）

用扩展的SELECT ... GENERATE触发生成

用标准SQL查询、过滤、导出生成结果

三、计算引擎：执行计划与三大支柱调度
3.1 核心问题
用户的一条生成查询（例如SELECT GENERATE(*) FROM sensor_data WHERE wind_speed < 25）在内部不是一步完成的。它必须经过一个执行计划，协调物理引擎、数据引擎和约束引擎。

计算引擎的核心职责是：将声明式生成请求，编译为三大支柱的操作符DAG（有向无环图），并选择最优执行路径。

3.3 引擎选择的决策逻辑
计算引擎在编译时，根据当前系统状态（参考理论框架第七节退化表）决定执行路径：

条件	执行路径	物理引擎	数据引擎	约束引擎
约束完备+数据充足+融合可用	全功能	提供约束域	生成分布	融合生成
约束完备+数据充足+融合不可用	后筛选	提供约束域	全量生成	过滤
约束完备+数据不足	纯物理	采样生成	禁用	跳过
约束不完备+数据充足	统计生成	禁用	生成	跳过（身份切换）
约束不完备+数据不足	退化	禁用	KDE扰动	跳过
3.4 引擎间的接口
计算引擎本身不实现物理仿真或深度学习。它只做调度。

引擎	输入	输出
物理引擎	约束卡片（CHECK/域定义）、采样参数	数据行（满足约束）
数据引擎	训练数据表、生成数量	数据行（统计相似）
约束引擎	候选数据行、约束卡片	数据行（过滤后）+ 排除报告
三个引擎各自独立部署和扩展，计算引擎通过统一接口调用。

四、存储引擎：不可变事实与版本时间线
4.1 核心问题
SynthGen Core的存储不像业务系统——它需要存储的不是“用户订单”，而是：

输入的真实数据（不可篡改的事实）

生成的合成数据（带完整provenance）

生成模型的版本（可回滚、可比较）

约束卡片（可演化）

审计日志（不可删除）

这决定了存储引擎的设计必须围绕不可变性和时间版本。

4.2 存储分层
text
┌──────────────────────────────────────────┐
│              审计日志层                   │
│  (WAL / 不可变追加)                       │
│  记录：谁在何时做了什么操作                │
├──────────────────────────────────────────┤
│              快照层                       │
│  (生成数据 + provenance + tail_report)    │
│  按版本号组织，不可变                      │
├──────────────────────────────────────────┤
│              模型层                       │
│  (生成模型参数/检查点)                     │
│  版本链：v1 → v2 → v3                     │
├──────────────────────────────────────────┤
│              基表层                       │
│  (用户上传的真实数据 + 约束卡片定义)        │
│  原始不可变，新数据追加                    │
└──────────────────────────────────────────┘
4.3 不可变性设计原则
与理论框架的可追溯性和审计不可变原则对齐：

基表层：用户上传的每批数据，写入后不可修改。新数据追加为新分区/新表。

快照层：每次生成产出的数据，一旦构建完成即不可变。

模型层：每次对齐后的模型参数，写入后不可变，形成版本链。旧版本不删除。

审计日志层：只追加，不可删除。

“删除”操作在物理层面不存在。 逻辑删除通过标记实现（如标记某版本为deprecated），物理存储永远保留。

4.4 版本时间线
存储引擎的核心抽象是版本时间线：

text
时间轴 ──────────────────────────────────────────▶

基表:    [v1 初始数据] ──▶ [v2 追加新批次] ──▶ [v3 再追加]
           │                    │                 │
模型:      └──▶ gen_v1           └──▶ gen_v2       └──▶ gen_v3
                  │                    │                 │
快照:             └──▶ snap_v1_001     └──▶ snap_v2_001  └──▶ snap_v3_001
                                                          snap_v3_002
每个基表版本可追溯。

每个生成模型知其基于哪个基表版本训练。

每个生成快照知其由哪个模型版本产生。

用户可以通过时间旅行查询任意历史快照。

五、三大模块的交互边界
模块	对外职责	不负责
接口层	解析SQL/声明式请求，返回结果集	不执行生成逻辑，不做存储管理
计算引擎	编译执行计划，调度三大引擎，组装结果	不暴露接口，不管理持久化
存储引擎	持久化基表、快照、模型、日志，支持时间旅行	不理解生成逻辑，只管理字节和元数据
三者之间通过内部协议传递数据：接口层 → 计算引擎（查询请求） → 存储引擎（读基表/写快照） → 返回 → 接口层。

六、为什么这个框架比“API+微服务”更好？
对比维度	API+微服务方案	AI原生数据库方案
Schema约束	需自行实现校验层	复用数据库Schema引擎
查询生成结果	需设计REST查询语言	直接SQL，无需设计
版本管理	需自行实现快照机制	复用MVCC/时间旅行
审计日志	需自行实现	复用WAL
权限控制	需自行实现	复用GRANT/REVOKE
存储优化	需自行调优	复用数据库成熟引擎
生态集成	每个系统单独对接	JDBC/ODBC 通用接入
核心洞察：我们不是在“用数据库存数据”，而是“把整个生成器做成数据库”。这不是比喻，是架构选择。
