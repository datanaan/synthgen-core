## 总览

工程文档试图将 SynthGen Core 定位为"AI原生数据库"，以类SQL接口对外、计算引擎调度三大支柱、存储引擎管理不可变版本时间线。架构愿景宏大，但工程可行性论证不足——多处核心声称在技术事实上不成立，且与理论框架的承诺存在实现能力缺口。

**致命问题 3 个 | 高优先级 4 个 | 中优先级 2 个**

## 🔴 致命级攻击

### 攻击一：核心前提不成立——你不是数据库，你是一个套了数据库壳的推理服务

**文档声称**（第一节）：生成操作映射为 `SELECT ... WITH GENERATE`，"如果你做一个生成器，却从零开始写存储、查询、日志、权限系统，你就是在重复发明数据库。不如直接以数据库为骨架。"

**事实反驳**：

这个推理有致命的逻辑跳跃。火箭发射的所有操作也是对数据的变换、存储和检索（轨道计算=变换，遥测存储=存储，参数查询=检索），但没人把火箭控制系统做成数据库。

问题出在**生成**这个操作上。数据库的 SELECT 是从已有数据中检索，GENERATE 是从模型中采样——这是推理(inference)，不是检索(query)。这两者的计算特征完全不同：

| 维度 | 数据库 SELECT | GENERATE |
|------|--------------|----------|
| 计算模式 | 确定性 | 随机性（采样） |
| 结果可复现 | 相同SQL→相同结果 | 相同SQL+不同seed→不同结果 |
| 计算成本 | I/O主导 | GPU/推理主导 |
| 内存模型 | 流式/游标 | 需要模型常驻内存 |
| 错误模式 | 语法错误/空结果 | 模式坍缩/分布偏移/排除率爆炸 |

**"复用数据库生态"在核心功能上不成立**：

1. **PostgreSQL 不支持 GENERATE 语法**。要加这个，你需要 fork PostgreSQL 源码，修改 `gram.y`（语法解析器）、增加 Custom Scan Provider、重写部分优化器逻辑。PostgreSQL 的 Custom Scan API 文档明确标注为"实验性功能"，且只能替换已有执行路径，不能添加新的语法节点。
2. 任何使用你系统的用户，不能用标准 PostgreSQL 客户端连接——他们需要用你的 fork。JDBC/ODBC 驱动在遇到 `GENERATE` 关键字时会直接报语法错误。
3. 你在7.2节自己承认需要自研"GENERATE 语法扩展和对应的查询计划节点"——这意味着你的 SQL 不是标准 SQL，你的数据库不是标准数据库。
4. 你声称的 JDBC/ODBC 通用接入（第六节对比表）在你的核心功能上直接失败。

你复用的是外围（WAL、MVCC、GRANT），但这些外围用任何成熟框架都能实现。你选择的最重架构决策（fork PostgreSQL）恰恰是为了实现那个"不能复用"的部分。

**守门要求**：重新评估架构选型。给出以下三种路径的诚实对比：

| 路径 | 描述 | 优势 | 代价 |
|------|------|------|------|
| 1. Fork PostgreSQL | 当前方案 | 完整数据库能力 | 维护不兼容fork、C生态与Python模型缝合、PG大版本升级跟踪 |
| 2. DuckDB扩展 | 嵌入式+自定义函数 | 轻量、进程内、列式 | 扩展能力有限、无WAL/MVCC、单进程 |
| 3. 自研查询层+PG存储后端 | 查询层独立开发，PG仅存数据 | 最灵活、生态隔离 | 不"像数据库"、需自建查询层 |

当前文档选了路径1但没有给出理由，更没有评估代价。**一个架构选择如果没有评估替代方案和代价，就是信仰，不是决策。**

### 攻击二：后筛选 = 拒绝采样，排除率高时系统崩溃

**文档声称**（3.3节）：约束完备+数据充足+融合不可用时，走"后筛选"路径——数据引擎全量生成，约束引擎过滤。

**事实反驳**：

这是经典的**拒绝采样(Rejection Sampling)**。它在理论上是正确的，但在工程上有已知的致命问题：**当约束区域只占生成分布的一小部分时，接受率趋于零，系统效率崩溃。**

理论框架 v1.2 已经定义了物理约束排除率>0.9时系统应降级。但工程文档完全没有讨论实现细节：

1. **排除率是运行时才能知道的**——你不知道要生成多少行才能凑够用户要求的行数。如果用户要1000行，排除率95%，你需要生成20000行，过滤掉19000行。
2. **内存分配**——数据库为 SELECT 结果预分配内存。20000行的内存只产出1000行，浪费95%内存。这还不算模型推理的GPU内存。
3. **延迟不可预测**——排除率90%和99%的区别是10倍生成量，但用户无法预知查询需要多久。一个"1秒"的查询可能变成"10秒"甚至"100秒"。
4. **恶性循环**——当排除率>95%时，增加生成量本身可能改变系统负载，导致模型推理变慢，进一步增加延迟。

**后筛选路径不应是无条件的默认选项。** 它应该是一种受监控的降级手段，有明确的前置检查和保障机制。

**守门要求**：

1. **定义生成请求的超时和行数保障机制**：如果N秒内无法生成足够行数，返回已生成的部分 + 排除率报告 + `data_grade` 降级标记，而非无限循环。
2. **在执行计划编译阶段，利用约束卡片的域信息预估排除率**。如果预估>0.9，直接拒绝走后筛选路径，强制走纯物理路径或要求用户放宽约束。
3. **定义排除率与 `data_grade` 的联动**：排除率0-30%→`physics_guaranteed`，30-70%→`statistics_guaranteed`，70-90%→`limited_fidelity`，>90%→拒绝生成。这与理论框架6.4节的尾部裁剪报告对齐。

### 攻击三：WAL ≠ 审计日志，不可变性声称不成立

**文档声称**（4.3节）："审计日志层：只追加，不可删除"，并在表格中映射为"WAL / 不可变追加"。

**事实反驳**：

**WAL (Write-Ahead Log) 是崩溃恢复机制，不是审计日志。** 两者的本质区别：

| 特性 | WAL | 审计日志 |
|------|-----|---------|
| 目的 | 崩溃后恢复一致状态 | 记录谁做了什么 |
| 保留策略 | checkpoint后可截断回收 | 不可截断 |
| 内容 | 物理页修改（二进制） | 语义操作（谁/何时/什么） |
| 不可篡改性 | 无保证（`pg_resetwal`可重置） | 需要 WORM + 数字签名 |
| 查询能力 | 不支持（二进制格式） | 必须支持 |
| 与理论框架9.3节的关系 | 无法支撑刚性声明 | 可以支撑 |

PostgreSQL 的 WAL 在 checkpoint 后会被回收。`pg_resetwal` 工具可以直接重置 WAL。`pg_waldump` 可以查看但不是审计级别的语义记录。

你的理论框架 v1.2 的9.3节做了刚性声明——"破坏协议就是退出框架，输出数据不享有任何理论保证"。如果审计日志可以被修改（WAL可以被截断/重置），你的刚性声明就没有技术基础。

基表层的"不可修改"同样没有技术保证——PostgreSQL 的 UPDATE/DELETE 是可以修改基表的，没有内置的"只允许 INSERT"表级别约束。

**守门要求**：

1. **将审计日志从 WAL 中分离**，设计为独立的 append-only 存储。选项包括：
   - 单独的审计表 + 触发器（轻量但不防DBA篡改）
   - Apache Iceberg snapshot 机制（不可变快照）
   - WORM 存储（如对象存储的合规保留策略）
   - 哈希链（每条记录包含前一条的哈希，形成 Merkle 链）
2. **基表层强制只允许 INSERT**。实现方式：`BEFORE UPDATE/DELETE` 触发器抛出异常，或使用 PostgreSQL 的 Row Security Policy。
3. **审计日志不可篡改性需要技术保证**，至少实现哈希链校验，而非仅靠声明。

## 🟠 高优先级攻击

### 攻击四：执行计划有编译没有优化——这不是引擎，是调度器

**文档声称**（3.1节）：计算引擎"编译为操作符DAG并选择最优执行路径"。

**事实反驳**：

3.3节的"决策逻辑"是一张5行的条件表——这不是优化，是**硬编码的 if-else**。

真正的数据库优化器做的是：
- **代价估计**：对不同执行路径估算 I/O、CPU、内存开销，选择代价最低的
- **逻辑优化**：谓词下推、投影裁剪、连接重排序
- **物理优化**：索引选择、并行度决策、内存分配

你的"计算引擎"做的是：查一张5行表，走固定路径。**这不是计算引擎，是路由器。**

更严重的问题是：**你没有给出"最优"的定义**。当约束完备+数据充足+融合可用时，你选"全功能"路径——但三个引擎的执行顺序是什么？如果数据引擎生成的100万行中，99万行会被约束引擎过滤掉，是否应该让物理引擎先采样再让数据引擎微调？这需要代价估计才能决策。

**守门要求**：

1. **诚实命名**：当前组件是"执行路由器"而非"计算引擎"。不要用"最优执行路径"这个词。
2. **给出需要代价估计才能决策的场景示例**（如后筛选效率问题）。
3. **声明优化器是第几版的交付内容**，v1至少需要什么级别的代价估计能力。
4. **定义"最优"的度量标准**：延迟？内存？排除率？生成质量？这些目标之间可能冲突。

### 攻击五：SQL CHECK 约束表达力天花板严重限制约束引擎

**文档声称**（2.2节理由二）："物理约束映射为SQL CHECK约束或WHERE子句，不需要新语言。"

**事实反驳**：

SQL CHECK 约束的表达力天花板极低，无法覆盖理论框架约束卡片的大部分需求：

| 约束类型 | 示例 | SQL CHECK 能否表达 |
|----------|------|-------------------|
| 单列范围 | `wind_speed ∈ [0, 25]` | ✅ |
| 单列枚举 | `status IN ('active', 'idle')` | ✅ |
| 跨列条件 | "风速>15时，风向必须偏北" | ⚠️ 笨拙（CASE WHEN + CHECK） |
| 跨行聚合 | "每小时平均温度≤40°C" | ❌ CHECK不支持聚合 |
| 时序单调 | "时间戳必须递增" | ❌ 无法引用其他行 |
| 概率约束 | "95%样本在μ±2σ内" | ❌ 完全超出SQL能力 |
| 物理方程 | "PV = nRT" | ❌ 多变量方程 |
| 自相关约束 | "相邻采样点变化率<阈值" | ❌ 需要窗口函数 |

**结果**：能表达的约束只有简单范围检查。复杂约束退回应用层校验，这破坏了"复用数据库约束引擎"的核心论点，也破坏了约束在数据库层面强制执行的安全保证。

**守门要求**：

1. **诚实声明 SQL CHECK 的表达力边界**——列出能表达和不能表达的约束类型。
2. **给出无法映射为 SQL CHECK 的约束的替代实现路径**：约束描述 DSL（如约束卡片的 YAML/JSON 形式）+ 运行时校验器。
3. **不能假装"不需要新语言"**——你很可能需要一个约束描述语言，它比 SQL CHECK 更强，比通用编程语言更受限（为了保证可验证性）。
4. **定义约束验证的执行位置**：哪些在数据库层执行（CHECK），哪些在计算引擎执行（运行时校验），保证没有约束被遗漏。

### 攻击六：模型层版本链无限增长，没有 GC/Compaction 策略

**文档声称**（4.3节）："旧版本不删除"，"物理存储永远保留"。

**事实反驳**：

每个模型版本可能几百MB到几GB。如果每天对齐一次（理论框架5.1节持续对齐），一年就是365个模型版本。10GB/版本 × 365 = **3.65TB/年/模型**。100个数据表 = **365TB/年**。

"物理存储永远保留"在工程上不可持续。

理论框架 v1.2 的记忆策略（第八节）给出了5种策略，但工程文档完全没有讨论如何与版本管理联动：
- 哪些旧模型版本可以被 compaction？
- 当记忆策略选择"滑动窗口"时，窗口外的模型是否可以物理删除？
- 版本保留与证据追溯之间的矛盾如何解决？追溯需要旧版本，存储需要清理旧版本。

**守门要求**：

1. **定义版本保留策略**——至少给出"默认保留N个版本，超出可配置"的机制。
2. **定义 compaction 规则**——何时可以将多个微版本合并为一个快照版本。
3. **声明物理删除的条件**——在什么前提下，旧版本可以被安全物理删除而不破坏可追溯性。建议：保留版本链的元数据（模型hash、训练数据版本、性能指标），但可以物理删除模型参数本身，前提是元数据足以重建证明链。
4. **与记忆策略联动**——不同记忆策略对应不同的版本保留策略。

### 攻击七：三大模块交互协议是空壳

**文档声称**（第五节）："三者之间通过内部协议传递数据。"

**事实反驳**：

**什么协议？** 没有定义。关键问题全部悬空：

| 交互方向 | 未定义的关键问题 |
|----------|----------------|
| 接口层 → 计算引擎 | 查询请求的内部表示？AST？逻辑计划？ |
| 计算引擎 → 存储引擎 | 读基表的数据传输格式？列式？行式？流式？ |
| 计算引擎 ← 存储引擎 | 模型参数如何加载？全量？按需？mmap？ |
| 存储引擎 → 接口层 | 生成结果的传输方式？一次性？游标？流式？ |
| 计算引擎 → 数据引擎 | 生成请求的参数传递？seed如何确定？ |
| 数据引擎 → 计算引擎 | 生成结果如何返回？批量？流式？背压如何处理？ |

没有协议定义，模块边界就是纸上的画——实现时一定会穿透。

**特别致命的交互**：计算引擎与数据引擎。数据引擎需要加载整个模型到内存才能生成，还是可以流式生成？如果是全量加载，当模型>内存时怎么办？如果是流式，计算引擎如何估算生成进度和剩余时间？

**守门要求**：定义至少三个关键内部协议：

1. **查询协议**（接口层 → 计算引擎）：请求格式、解析结果格式、错误传播
2. **数据协议**（计算引擎 ↔ 存储引擎）：数据传输格式、模型加载方式、流控机制
3. **生成协议**（计算引擎 ↔ 数据引擎）：生成请求格式、结果返回方式、进度报告、背压机制

每个协议需要定义：数据格式、传输方式、错误处理、背压机制。

## 🟡 中优先级攻击

### 攻击八：声称比"API+微服务"更好，但对比是不公平的

第六节的对比表只列了"数据库方案更好"的维度。缺失的关键维度：

| 维度 | 数据库方案 | API+微服务方案 |
|------|-----------|---------------|
| 部署复杂度 | 需要 fork 并维护 PostgreSQL | 标准 Docker 容器 |
| 开发速度 | 需要理解 PG 内部架构 | 标准 Web 开发 |
| 水平扩展 | PG 扩展困难（你7.3节也承认） | 微服务天然支持 |
| 迭代灵活性 | 修改需重新编译数据库 | 独立部署各服务 |
| 人才可得性 | 需要 PG 内核开发者（稀缺） | 标准 Python/Go 开发者 |
| **生成模型集成** | **需在DB进程内加载PyTorch** | **模型作为独立服务部署** |

最后一点是核心矛盾：**生成模型（深度学习）天然是 Python 生态，PostgreSQL 天然是 C 生态。** 在数据库进程内加载 PyTorch 模型，需要处理：
- Python GIL 与 PG 进程模型的冲突
- PG 的内存管理（palloc）与 PyTorch 的内存管理（CUDA allocator）的冲突
- 模型推理崩溃导致数据库进程崩溃的风险隔离
- GPU 资源在多个数据库会话间的竞争

这不是"复用生态"，是**生态缝合**——把两个完全不兼容的运行时硬塞进一个进程。

**守门要求**：

1. 补充公平对比表，包含数据库方案的劣势维度。
2. 评估在数据库进程内加载深度学习模型的技术可行性——给出至少一个成功案例（如 Apache MADLib、PostgresML）的架构分析和局限性。
3. 如果不走数据库方案，WAL/MVCC 等是否有轻量替代（如 SQLite 的 WAL + 应用层审计日志）。

### 攻击九：暂不承诺的部分与理论框架的时效性承诺矛盾

**文档声称**（7.3节）：不在第一版引入实时流式生成。

**事实反驳**：

理论框架 v1.2 的5.1节"持续对齐"和5.2节"代偿机制"隐含了实时或准实时的数据流——"随着新数据持续输入，更新生成模型"。

如果持续对齐只能做批量（每天/每小时），意味着：
- 漂移检测的延迟是批量间隔
- 代偿模型的启动延迟也是批量间隔
- 在两次批量对齐之间，系统可能已经在用退化模型生成数据

**你的理论框架的时效性承诺和工程框架的实现能力之间存在差距。**

更具体地说：理论框架5.2节的漂移/演化检测依赖"新数据持续输入"——如果输入是批量的，检测就是滞后的。一个在T+1才检测到的漂移，意味着T到T+1之间生成的所有数据都是基于退化模型的。

**守门要求**：

1. **明确持续对齐的最小周期**（秒级？分钟级？小时级？）。
2. **声明对齐周期对理论框架5.2节漂移检测的影响**——在两次对齐之间，系统以什么 `data_grade` 运行？
3. **定义最小可行周期**——理论框架要求的最小频率是多少？低于这个频率，理论保证是否失效？
4. 如果要实现秒级/分钟级，给出架构变更方向（如微批处理、增量模型更新）。

## 守门员裁定

**❌ 工程设计 v0.1 不通过。需要重大修订。**

核心问题不是细节不够，而是**架构选择的论证不诚实**：
- 你选择了一个最重的架构（fork PostgreSQL），但没有评估替代方案和代价
- 你声称"复用生态"，但核心功能恰恰不能复用
- 你声称"不可变"，但没有技术保证
- 你声称"最优执行路径"，但只有5行if-else

**理论框架通过审查是因为它诚实——诚实声明了偏差、条件、红线。工程框架需要同样的诚实。**

**修订优先级**：
1. 🔴 首先解决攻击一——架构选型论证是地基，地基不稳则全盘动摇
2. 🔴 然后解决攻击二和三——后筛选崩溃和审计不可变是功能性和安全性的硬伤
3. 🟠 再解决4-7——命名诚实、约束边界、版本GC、协议定义
4. 🟡 最后解决8-9——对比公平性和时效性缺口

**期望：v0.2 能在架构选型上给出诚实的三种路径对比，在后筛选和审计层给出可落地的技术方案。**
