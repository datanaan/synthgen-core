## 二、逐层回溯：产品 → 价值 → 理论 → 工程

### 2.1 产品层的承诺

**一句话定位**：面向工业AI的智能合成数据引擎
**核心交付**：输入场景需求 → 输出带标注、可追溯、物理自检的高质量模拟数据集
**产品形态**：本地部署的软件套件（核心引擎 + CLI/API + 可选Web控制台）

**目标客户**：
1. 工业AI团队（核心）—— 故障数据稀缺、标注成本高、边缘场景不足
2. 工业设备制造商（增值）—— 仿真太慢，需要AI增强
3. ISV（生态）—— 嵌入产品栈，标准化数据生成

**定价**：按生成数据价值，不按计算资源

### 2.2 价值层的承诺

五个独立维度，每一个都声称"不依赖外部验证端"：

| 维度 | 承诺 | 依赖 |
|------|------|------|
| 替代不可采集数据 | 生成物理可能的数据 | 物理约束卡片 |
| 替代标注 | 自动附加精确真值 | 仿真构造 |
| 覆盖参数空间 | 系统性探索未见过区域 | DomainPack |
| 可复现 | 完整provenance | 版本管理 |
| 效率提升 | 比传统仿真快1-2个数量级 | 数据驱动生成 |

### 2.3 理论层的约束

v1.2 理论框架在五个价值上叠加了严格的条件：

- 价值1（替代不可采集数据）→ 物理合法性有条件保证（约束完备时），约束缺失时身份切换
- 价值2（替代标注）→ 标注精度受排除率影响，排除率>90%时拒绝生成
- 价值3（覆盖参数空间）→ 物理优先导致尾部风险被系统性裁剪（认识论偏差）
- 价值4（可复现）→ compaction 后时间旅行退化，偏差报告替代精确复现
- 价值5（效率提升）→ 聚合约束的两阶段执行比逐行慢，后筛选大量丢弃时效率归零

### 2.4 工程层的实现

v0.4 工程框架把理论约束翻译为：
- SynthLang（自研语言）
- 三类约束执行模型（值域/行间/聚合）
- 执行路由器（退化路径）
- 后筛选保障（排除率预估+超时截断）
- StorageBackend（可插拔存储）
- 哈希链审计日志
- 模型版本GC

## 三、🔴 路线偏移检测

### 偏移一：产品形态从"软件套件"漂移为"数据库"（🟠 高）

**产品层声称**：本地部署的软件套件（核心引擎 + CLI/API + 可选Web控制台）

**工程层实现**：生成原生数据库，自研 SynthLang 语言，DDL 类型系统

**偏移**：从"软件套件"变成了"数据库产品"。这不是命名问题——数据库产品意味着：
- 用户需要理解 SynthLang（一种新语言）
- 用户需要理解 DDL/Schema 定义
- 用户需要用 GENERATE TABLE ... FROM ... WITH CONSTRAINTS 这种声明式语法

**问题**：你的目标客户是**数据工程师、ML工程师**，不是**DBA**。他们习惯 Python SDK + REST API，不习惯写一种新查询语言。

**产品层的定价维度**中，没有"学习 SynthLang 的成本"这一项。但学习成本是真实的——客户需要培训才能使用一种自研语言。

**严重性评估**：如果 SynthLang 只是内部IR（中间表示），而用户通过 Python SDK / REST API 交互，这不是问题。但如果用户需要直接写 SynthLang，**产品门槛与目标客户不匹配**。

**结论**：v0.4 的文档没有明确区分"SynthLang 是用户直接书写的语言"还是"SynthLang 是内部编译目标"。如果是后者，偏移可消除。如果是前者，需要重新评估用户门槛。

---

### 偏移二：五个价值的交付依赖与产品承诺不一致（🟠 高）

**价值层声称**：五个价值"没有一个需要 Polymorphic-Twin 来盖章"

**理论层的现实**：

| 价值 | 产品层承诺 | 理论层条件 | 缺口 |
|------|-----------|-----------|------|
| 替代不可采集数据 | "有比没有好" | 约束缺失时身份切换为统计相似生成器，安全关键硬拒绝 | 客户恰好是安全关键场景（第一梯队核心客户），"有比没有好"不成立 |
| 替代标注 | "精确真值" | 排除率>90%拒绝生成；排除率30-70%时误差界放宽 | 客户买的精确标注，拿到的是放宽了误差界的标注 |
| 覆盖参数空间 | "系统性探索" | 物理优先导致尾部裁剪 | 客户需要的恰好是尾部（极端工况），被裁掉了 |

**这三个缺口不是工程缺陷，是理论层比产品层更诚实的结果**。但产品文档没有同步理论约束。

**后果**：销售按照"五个独立价值"承诺，交付时受理论约束限制。客户预期与实际交付之间的落差，是最大的商业风险。

---

### 偏移三：目标客户画像与约束卡片依赖的矛盾（🟠 高）

**产品层**：核心客户是"工业AI团队（10-100人）"

**理论层**：三大支柱中，物理驱动的工程可行性**需要领域专家编写约束卡片**

**矛盾**：10-100人的AI团队中，**有多少人能写约束卡片？** 约束卡片需要的是物理/工程领域专家，不是ML工程师。产品层的目标客户画像（数据工程师、ML工程师、仿真工程师）中，只有仿真工程师可能有这个能力。

**理论层承认了这个风险**（3.1："约束卡片的编写需要领域专家。若无专家，此支柱退化"），但产品层没有把这个前提条件放在客户画像的必要条件中。

**更严重的是**：如果客户没有领域专家，系统退化为"统计相似数据生成器"——而产品层的定价中，"基础许可费+场景数量"是按物理引擎后端计费的。客户付了物理引擎的钱，拿到的是统计生成器的产出。

---

### 偏移四：定价维度与工程架构不对应（🟡 中）

**定价维度**：
- 基础许可费（含物理引擎后端）
- 场景数量（每个DomainPack）
- 高级后端（PINN生成器、LLM编译器、反例搜索）
- 生成数据量阶梯

**工程架构**：执行路由器根据约束完备性和数据充足性自动选择路径。客户无法控制走哪条路径。

**问题**：
1. 客户买了 PINN 生成器，但执行路由器判定数据不足，走了纯物理路径——PINN 生成器没用到，客户感知是"高级功能买了但没用"
2. 客户买了基础许可，但约束缺失时系统自动退化为统计生成器——基础许可含物理引擎，但物理引擎没用到

**根本原因**：定价按功能模块，但工程上路径选择是自动的。客户付费的模块可能不被激活。

---

### 偏移五："反例搜索"在理论框架和工程框架中完全消失（🟡 中）

**产品层**明确列出"反例搜索模式：主动寻找使目标模型失效的数据点"

**价值层**也隐含了这个方向（覆盖参数空间 → 探索失效边界）

**理论框架 v1.2**：没有任何关于反例搜索的理论基础。退化和失败模式都是被动响应（数据不足→退化），不是主动探索。

**工程框架 v0.4**：没有任何反例搜索的实现设计。

**偏移**：产品层承诺了一个高价值功能（对第二梯队客户——设备制造商尤其重要），但理论和工程都没有跟进。这不是"推迟"，是**遗漏**——因为没有人注意到它消失了。

---

### 偏移六：持续对齐的理论承诺与工程实现的时间尺度差异（🟡 中）

**理论层**5.1节："随着新数据持续输入，更新生成模型对分布密度的估计"

**产品层**："不接入实时生产数据流"

**工程层**：`UPDATE GENERATION MODEL ... INCORPORATE DATA FROM sensor_log WHERE timestamp > ...`

**偏移**：产品说"不接入实时"，理论说"持续"，工程实现的是**批量**（手动触发 UPDATE）。三者对"持续"的时间尺度理解不一致。

- 产品层：永远不接入实时（产品边界）
- 理论层：暗示准实时（漂移检测）
- 工程层：手动批量（用户主动触发）

**漂移检测的延迟取决于批量间隔**。如果用户每天触发一次，漂移检测的延迟就是一天。这对工业场景够不够？产品层需要声明。

## 四、理论框架自身的潜在缺陷

### 缺陷一：身份切换的触发是静态的，缺少运行时动态切换

理论层7.2节的身份切换是**基于约束状态**的静态判断——约束完备→物理合法生成器，约束不完备→统计相似生成器。

但实际场景中，**约束完备性可能在一次生成会话内变化**：
- 用户先定义了完整的约束卡片（身份：物理合法）
- 生成过程中发现约束卡片有遗漏（部分参数空间未被覆盖）
- 此时身份应该切换吗？

理论层说"约束真空时降级标记"（6.2节），但没有说**身份是否在运行时动态切换**。如果是动态切换，一个 GENERATE 请求可能产出两种身份的数据——这需要 EvidencePackage 按行标记身份，而不是按请求标记。

### 缺陷二：代偿机制的收敛条件缺失

5.3节代偿机制：漂移检测→冻结核心模型→启动代偿通道→用户判断→收束。

"用户判断"后的收束有三种路径：合并/保留为条件分支/废弃。但没有给出**收束的判断标准**——用户依据什么做决策？系统应该提供什么信息辅助决策？

如果用户迟迟不判断（忘了、不确定），代偿通道是否永远运行？代偿模型的存储是否永远增长？

### 缺陷三：记忆策略"待工程细化"的空白

理论层第八节说"此策略体系待工程细化，当前无显著可行性风险"。但终审报告留下的两个非阻断观察之一就是"记忆策略需要补充退化分析——如果五项策略全部失败，持续对齐如何退化"。

五项策略全部失败不是不可能——如果存储资源耗尽，所有记忆策略都无法执行。此时持续对齐退化为什么？理论层没有回答。

---

## 五、工程框架自身的潜在缺陷

### 缺陷一：SynthLang 的语法能力边界未声明

v0.4 的 SynthLang 语法越来越丰富（ORDER、DURING ... =、WHEN ... THEN、OVER 窗口），但**语法的表达能力边界**从未声明。

用户能写子查询吗？能写 CTE 吗？能写递归约束吗？能引用其他约束卡片吗？

类比 PostgreSQL：它的语法能力边界是 SQL 标准 + 扩展。SynthLang 的边界是什么？如果不在 v1 就声明，用户会不断试探边界，每个试探都是一次 bug 报告。

### 缺陷二：模型推理路径（ONNX/TensorRT）与数据库引擎的进程模型冲突

工程层声明"模型推理走 ONNX Runtime 或 TensorRT"。这两种运行时的特征：
- ONNX Runtime：C++ API，可嵌入进程，但有内存峰值（模型加载时）
- TensorRT：构建引擎耗时长（分钟级），推理快（毫秒级），适合长驻

如果 SynthGen Core 是数据库式的长驻进程，模型推理可以嵌入同一进程。但如果多个 GENERATE 请求并发使用不同模型，**进程内内存压力**如何管理？

工程层没有讨论进程模型——单进程？多进程？模型按需加载还是预加载？这直接影响并发能力和内存规划。

## 七、裁定与建议

### 路线偏移总体评估

**没有致命的方向性错误。** 核心理论（物理优先、条件保证、身份切换）经过三轮对抗性审查，已经非常坚实。工程框架 v0.4 也没有架构方向的硬伤。

**但存在系统性的"诚实梯度"问题：理论层最诚实，工程层次之，产品层最不诚实。** 理论层声明了所有条件和限制，工程层继承了大部分，产品层几乎没有同步这些限制。

### 需要立即修复的（🟠 高）

1. **产品层同步理论约束** — 重新撰写"五个独立价值"，在每个价值后附加"理论条件"列。销售人员必须知道物理合法性是有条件的，标注精度受排除率影响。

2. **声明 SynthLang 的定位** — 是用户直接书写的语言还是内部IR？如果是后者，产品层继续说"CLI/API"；如果是前者，需要在客户画像中加入"需要学习成本"。

3. **约束卡片编写者纳入客户画像** — 目标客户不只是AI/ML工程师，必须有领域专家（或购买场景定制服务）。这影响销售策略和定价。

### 需要尽快补完的（🟡 中）

4. **反例搜索的理论和工程** — 产品层承诺了但理论和工程都缺。要么补完，要么从产品边界中删除。

5. **持续对齐的时间尺度声明** — 产品层说"不接入实时"，理论层暗示"持续"，工程层是"手动批量"。需要统一语言。

6. **定价与执行路径的对应** — 客户为功能模块付费，但路径选择是自动的。需要声明"高级功能的激活取决于数据条件"。

7. **身份切换的运行时行为** — 一次生成会话中身份是否可以动态切换？EvidencePackage 是按请求还是按行标记身份？

### 可推迟的（🟢 低）

8. 记忆策略退化分析
9. 代偿机制收敛条件
10. SynthLang 语法能力边界声明
11. 模型推理进程模型

---

## 八、一句话总结

**理论和工程走对了路，但产品层没有同步理论层的诚实。** 理论层把"物理合法性有条件"写进了核心公式，产品层还在说"物理自检"。这个落差如果不补，客户会按"物理自检"的预期购买，按"条件保证"的实际交付——每次交付都是一次信任危机。
