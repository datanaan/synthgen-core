## 🟠 高优先级问题

### 问题一：约束类型的三类执行模型未区分

**5.1节**定义了两层约束架构，但**层次二**内部实际上包含三种语义完全不同的约束：

| 约束类型 | 示例 | 执行模型 | 类比 |
|----------|------|---------|------|
| 值域约束 | `wind_speed BETWEEN 0 AND 25` | 逐行检查 | CHECK constraint |
| 行间约束 | `vibration[t] - vibration[t-1] < 5.0` | batch 内有状态检查 | 窗口函数，需要 frame |
| 聚合约束 | `AVG(temperature) OVER (INTERVAL 1 HOUR) <= 40.0` | 两阶段执行 | HAVING + 窗口生成 |

**核心影响**：聚合约束改变了生成流程的粒度。

- 值域/行间约束：逐行生成→逐行检查→输出/丢弃
- 聚合约束：生成一个窗口→聚合→检查→全部输出/全部丢弃

这意味着：
1. 后筛选的粒度从"行"变成"窗口"
2. 排除率的含义变化——不是"丢弃的行占比"，而是"丢弃的窗口占比"
3. 执行路由器的退化表需要增加约束类型维度
4. 或在编译阶段将含聚合约束的请求重写为两阶段执行计划

**建议**：

```
编译阶段约束分类：
  IF 包含聚合约束 → 两阶段执行计划（生成阶段 + 验证阶段）
  ELIF 包含行间约束 → batch 有状态执行（维护 frame buffer）
  ELSE → 逐行执行（标准路径）
```

**补完要求**：在5.1节将层次二细分为 2a（行间约束）和 2b（聚合约束），并声明各自的执行模型差异。

### 问题二：GC 与时间旅行的退化行为

4.3节的 GC 保护条件基本正确（锚定保护 + 快照依赖保护 + 默认保留数），但有一个缺口：

**用户可能直接按版本名查询而不经过快照**。如 `AS OF MODEL VERSION gen_model_v2.3` — 这个版本可能没有被任何快照引用，但用户仍然需要它。

MVCC 的 vacuum 也有类似问题——PostgreSQL 的解决方案是：vacuum 不回收被任何活跃快照引用的版本。你的"快照依赖保护"就是这个思路，但保护范围只覆盖了"被快照引用"，没覆盖"被用户直接查询"。

**建议**：

1. GC 保护条件扩展为：**被快照引用 OR 被锚定 OR 在最近 N 个版本内**（N 可配置）
2. 定义时间旅行的退化行为：请求版本已被 compaction 时，返回最接近可用版本 + `version_mismatch: true` 标记 + 偏差报告
3. Compaction 后保留的元数据清单：模型参数 hash、训练数据版本、排除率、fidelity score、约束完备性标记

**补完要求**：在4.3节补充退化行为定义。

### 问题三：存储抽象层接口

"可插拔"需要类似 PostgreSQL `smgr` 或 SQLite VFS 的抽象层。对数据库团队这是标准工作，但 v0.2 没有定义接口。

**建议的最小接口定义**：

```
StorageBackend {
    // 写入
    append(table_id, batch: ArrowBatch) -> SnapshotRef
    append_model(model_id, checkpoint: bytes) -> VersionRef
    
    // 读取
    scan(table_id, snapshot_id, columns, predicate) -> ArrowBatchIterator
    load_model(model_id, version_id) -> CheckpointStream
    
    // 版本
    list_versions(table_id) -> [VersionMeta]
    get_snapshot(table_id, version_tag) -> SnapshotRef
    
    // 生命周期
    compact(table_id, version_range, strategy) -> CompactResult
    verify_audit_chain(from_seq) -> VerifyResult
}
```

v1 选一个默认后端实现（如对象存储 + Parquet + 自研元数据层），v2 再扩展其他后端。

**补完要求**：在第十节增加存储抽象层接口定义。

## 🟡 中优先级问题

### 问题四：预估算偏向性

体积比估算（selectivity estimation）在数据库优化器领域是老大难问题，PostgreSQL 的 `pg_statistic` 也只是统计近似。不需要精确解。

**建议**：采用数据库优化器标准做法——**基于直方图/采样的 selectivity 估计 + 保守偏向**。预估排除率时宁可高估，让系统倾向于走更安全的路径（类似 PG 优化器在不确定时偏向顺序扫描）。

**补完要求**：在3.2节声明预估算的保守偏向设计原则。

---

### 问题五：排除率与条件保证误差界的联动

排除率是工程指标，条件保证误差界是理论指标（理论框架 v1.2 §4.2）。两者需要独立测量但联动报告。

**建议**：EvidencePackage 同时包含两者，排除率>30%时条件保证误差界自动放宽（如双变量相关从 0.2→0.4），标记放宽原因。

**补完要求**：在3.2节的排除率→data_grade 联动表中增加误差界列。

---

### 问题六：哈希链的创世、分叉、验证频率

工程细节，补上即可：

1. **创世记录**：`prev_hash = SHA256("SYNTHGEN_GENESIS")` 或固定常量
2. **分叉检测**：写入时检查 `prev_hash` 是否与末尾记录 `current_hash` 一致，不一致则拒绝写入并报警
3. **验证频率**：写入时实时校验前一条 hash（O(1) 开销），每日全链遍历校验（O(n) 后台任务）

**补完要求**：在4.2节补充三个实现细节。
