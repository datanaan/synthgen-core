## 新发现的问题

### 问题一（🟠 高）：聚合约束两阶段执行跳过了值域约束

**位置**：3.2 类型三

**原文**：
> 阶段一：数据引擎全量生成（无约束过滤）
> 阶段二：按窗口聚合，检查约束。不满足约束的窗口内数据行全部排除

**问题**："无约束过滤"意味着连值域约束也被跳过。窗口内可能包含 `temperature = -99999`（越界值），污染聚合计算，导致本应通过的窗口被误判。

**修复建议**：两阶段执行不等于放弃所有约束。约束类型的分层本身就是执行顺序：

```
编译阶段约束分类逻辑（修订）:
  IF 包含聚合约束 → 两阶段执行计划
    阶段一：逐行过滤值域约束（如有行间约束，也在阶段一做）
    阶段二：窗口聚合验证（检查聚合约束）
  ELIF 包含行间约束 → batch 有状态执行
  ELSE → 逐行执行
```

**原理**：值域约束是最底层约束，必须最先执行。在聚合约束的场景下，值域约束仍应在逐行阶段完成——它不影响两阶段的架构，只是阶段一不应"全量无过滤"。

### 问题二（🟠 高）：行间约束缺少排序列绑定

**位置**：3.2 类型二, 2.2 语法

**问题**：`vibration[t] - vibration[t-1]` 的"前一行"由什么决定？当前约束定义语法没有指定排序依据。

PostgreSQL 窗口函数要求 `OVER (ORDER BY ...)` 显式指定排序列。行间约束同理。

**修复建议**：行间约束的语法需扩展排序依据。

方案A — 约束级别指定：
```
DEFINE CONSTRAINT wind_safety ON sensor_log
ORDER BY timestamp (
    vibration[t] - vibration[t-1] < 5.0
);
```

方案B — Schema 级别声明默认排序（推荐，减少重复）：
```
DEFINE TYPE sensor_log {
    timestamp: DATETIME NOT NULL ORDER,
    ...
};
```

方案B 更符合"Schema 强制"的设计原则，且避免每个约束卡片都重复声明排序列。

### 问题三（🟡 中）：聚合窗口类型扩展预留

**位置**：2.2, 3.2

**当前**：只有 `INTERVAL` 时间窗口。生成场景可能还需要行数窗口、分组窗口、会话窗口。

v1 不需要全部实现，但语法上需预留扩展点，避免后续改 parser。

**建议**：在语法设计中声明窗口类型的扩展路径：
```
OVER (INTERVAL 1 HOUR)         -- v1: 时间窗口
OVER (ROWS 100)                -- v2: 行数窗口
OVER (PARTITION BY x, INTERVAL) -- v2: 分组窗口
```

### 问题四（🟡 中）：StorageBackend 缺事务语义

**位置**：5.1

**问题**：快照写入（数据+provenance+tail_report）、模型版本+审计日志、compaction 操作都需要原子性。对象存储不提供事务，元数据层需承担。

**建议**：
- 在接口中增加 `atomic_write(operations: [WriteOp]) -> Result`
- 或声明元数据层负责事务协调，v1 实现两阶段提交或乐观并发控制

---

### 问题五（🟡 中）：约束完备度是连续值不是布尔值

**位置**：4.1

**问题**：执行路由器用布尔值（完备/不完备）判断。但"约束不完备"的范围差异巨大——缺1个约束和缺3个约束应走不同路径。

**建议**：引入约束完备度评分（0.0-1.0），作为执行路由器的连续输入。路由决策可以基于阈值分段（如 >0.7 走全功能，0.3-0.7 走统计生成，<0.3 走退化）。

---

### 问题六（🟡 中）：DURING 模式列未绑定

**位置**：3.2 类型二, 2.2

**问题**：`DURING 'normal_operation'` 是字面量，但系统不知道哪个列的值对应 `normal_operation`。

**建议**：
- 语法改为 `DURING status = 'normal_operation'`
- 或在 Schema 中声明 `MODE_COLUMN`

---

### 问题七（🟢 低）：协议错误处理未定义

**位置**：6.1-6.3

**问题**：只定义了正常路径，缺少错误处理。

**建议**：声明默认策略——任何组件失败→请求失败+审计日志记录+EvidencePackage 标记 failed。
