## 一句话

从自行车到跑车，每个阶段都能骑，每个阶段都更快——但每个阶段都背着诚实声明。

---

## 核心隐喻

想象你造一台车：

❌ **水平分层法**：先造完所有轮子，再造完所有发动机，再装所有车身，最后组装——前三个月你连车都看不到，只能看一堆零件。

❌ **垂直切片法**：先造一辆能跑的三轮车，再改装成四轮，再加发动机，再加空调——每次改装都要拆了重来，接口不断变。

✅ **能力里程碑法**：

```
v1 自行车    → 能骑，能到目的地，验证了"人能在这上面走"
v2 摩托车    → 有引擎，跑得快，验证了"动力系统可靠"
v3 轿车      → 有空调有导航，验证了"舒适性和智能化"
v4 跑车      → 极致性能，验证了"边界条件下依然可控"
```

每个阶段**完整可用**，每个阶段**自然进化**到下一阶段。

### v1.1 诚实修正

v1.0 说了"每个阶段自然进化，不需要拆了重来"。这不准确。

v1→v2 的进化**不是**在后座绑一个发动机。v1 的生成流程是"物理引擎采样→值域验证"，是单一固定路径。v2 引入执行路由器后，调度逻辑从硬编码变为路由驱动——这是改车架、传动、制动，是新的整车。

准确的说法：

**值域约束的验证逻辑不变（逐行检查 BETWEEN/MIN/MAX），但调度方式从硬编码变为路由器驱动。核心逻辑不推翻，但调度架构需要重构。**

摩托车不是自行车+引擎。摩托车是新车。但自行车的轮子（值域验证逻辑）还在摩托车上用。

## 为什么不选水平分层？

水平分层看起来"架构清晰"——先把接口层做完，再把引擎做完，最后做存储。

问题：**前三个月没有任何可运行输出。**

你无法验证：
- Parser 解析出来的语法树，生成引擎能不能用
- 存储层写进去的格式，约束引擎能不能读
- EvidencePackage 的字段定义，SDK 用户觉得够不够

等你发现接口不对，已经写了三个月。改接口 = 改三层 = 重来。

能力里程碑不存在这个问题。v1 两周后你就能跑端到端：数据进去→物理采样→验证→证据包出来。接口不对？当时就发现，当时就改。

---

## 为什么不选垂直切片？

垂直切片看起来"最快出活"——先做一个最小切片，逐步扩展。

问题：**早期切片的接口在扩展时要重构。**

比如第一刀切"只支持整数类型"，第二刀扩展浮点数，第三刀加时间类型——每次都要改 Parser、改存储、改引擎。改了三轮，最初的代码面目全非。

能力里程碑的风险更小。v1 按理论框架 v1.3 的分层设计——值域约束引擎的验证逻辑在 v2 不需要重构，v2 加的是行间引擎、聚合引擎和路由器调度。**理论已经告诉你分层是什么，路线就按分层走。**先有理论，后有路线。

但必须诚实：v1→v2 的调度重构是不可避免的。这不是"原封不动"。

---

## 为什么是这四个版本？

不是拍脑袋分的。是理论框架 v1.3 的约束分层决定的：

```
理论层          →  路线图版本
─────────────────────────────
值域约束（逐行）  →  v1 最小可运行
行间约束（有状态）→  v2 约束完整（加上行间+聚合）
聚合约束（两阶段）→  v2 约束完整（与行间同版本，因为阶段一包含行间）
─────────────────────────────
时间维度         →  v3 时间智能
窗口扩展+完备度  →  v4 高级分析
```

关键洞察：**聚合约束的两阶段执行中，阶段一就是值域+行间**。所以聚合约束不能脱离行间约束单独实现。它们天然属于同一个版本（v2）。

这不是我决定的，是数学决定的。

## 每个版本的"车"能做什么

### v1 自行车

- 定义数据长什么样（Schema，通过 Python SDK）
- 把真实数据搬进来（LOAD DATA）
- 告诉系统"温度不能超过80度"（值域约束）
- 物理引擎在约束域内采样
- 拿到物理合法的数据和证据包
- **tail_report 声明物理优先偏差**

**能骑了**。虽然只有单速，但你能从A到B。

**诚实声明**：v1 的数据世界比真实物理世界更窄。极端工况和尾部事件被值域约束系统性排除。这是理论选择，不是功能缺陷。每份 EvidencePackage 都会告诉你这件事。

### v2 摩托车

- 行间约束：相邻两行温度差不能超过5度
- 聚合约束：1小时内平均温度不能超过40度
- 执行路由器：5条退化路径，每条路径有身份声明
- 后筛选保障：排除率预估+保守偏向
- 审计日志：每一步操作都有哈希链可追溯
- **DURING/WHEN 条件约束**

**有引擎了**。不只能骑，还能在复杂地形上跑。

**诚实声明**：v2 的数据引擎参与后，统计签名保证变为有条件的。data_grade 从单一的 physics_guaranteed 扩展为多级条件保证。条件越宽松，保证越弱。

### v3 轿车

- 时间旅行：回到旧版本看看当时的生成结果
- 持续对齐：新数据来了，模型自动进化
- 模型版本管理：旧版本自动合并，但元数据保留
- tail_report 增强：误差界、fidelity_mismatch、代偿模型状态

**有导航和空调了**。不只是跑，还知道跑过哪里，跑到哪里去。

**诚实声明**：持续对齐引入了代偿模型。代偿模型在收敛时限内可能偏离原始约束。系统会定期提示未关闭的漂移事件，但代偿通道不会自动停止。

### v4 跑车

- 行数窗口/分组窗口/会话窗口：任意切法
- 约束完备度评分：0.0-1.0，不再是"有/没有"
- 反例搜索（研究性）：探索约束域边界——**如果理论和工程预研成功的话**

**极致性能和洞察**。不只是跑得快，还能看到看不见的。

**诚实声明**：反例搜索没有理论基础。v4 是否交付反例搜索，取决于 v2/v3 阶段的理论预研成果。这是研究性里程碑，不是产品承诺。

## 为什么 v1 选"最小可运行"而不是"约束完整"？

因为自行车比摩托车更早能骑。

v1 只做值域约束，6-7周就能看到端到端输出。如果 v1 就做三类约束，周期翻倍，前10周没有任何可演示成果。

更重要的是：**v1 的值域约束是 v2 聚合约束阶段一的基础**。没有值域约束，聚合约束的两阶段执行无从谈起。先造轮子（值域），再装发动机（行间+聚合），顺序不能反。

### v1 走哪条生成路径？

v1 走**纯物理采样**路径。值域约束直接作为采样边界，物理引擎在约束域内采样。不需要后筛选，不需要数据引擎训练。

为什么不走后筛选路径？因为后筛选需要数据引擎先训练模型再生成再过滤——v1 还没有数据引擎。纯物理采样是 v1 唯一可行的路径。

这也意味着 v1 的排除率应为 0%（物理引擎直接在约束域内采样，验证器应全部通过）。排除率不为 0 的场景从 v2 后筛选路径开始。

## 路线图必须背负的理论承诺

v1.0 的一个严重疏漏：理论框架 v1.3 花了三节（2.3、6.4、7.2）声明认识论偏差，但路线图——作为交付承诺的第一页——对此完全沉默。

路线图可以简化工程细节，但不能省略理论承诺。以下三个承诺从 v1 起就必须传递：

### 1. 认识论偏差声明

物理优先策略导致生成数据世界的风险谱比真实物理世界更窄。极端工况和尾部事件被系统性排除。

这不是 v1 的功能缺陷，是理论选择。但用户必须知道。

传递方式：v1 的每份 EvidencePackage 都包含 conservative_tail_report，声明偏差。

### 2. 条件保证

data_grade 不是"好/坏"的标签，是有条件的保证声明：
- physics_guaranteed：物理合法性无条件保证（v1 即提供）
- statistics_guaranteed：统计签名保证有条件（v2 起随数据引擎参与而生效）
- limited_fidelity：条件降级

传递方式：EvidencePackage 字段适用性标注。v1 中 statistical_fidelity 标记为 not_applicable，明确告知用户"此保证不可用"。

### 3. 身份切换

执行路由器的退化路径不是"降级"，是不同认识论承诺的声明。不同身份的生成器，承诺不同的事。

传递方式：v2 EvidencePackage 的 generator_identity 字段。

---

## 总结

路线图的选择逻辑，就三条：

1. **每个阶段都能骑**——端到端可运行，不是零件堆
2. **每个阶段自然进化**——前阶段的产出是后阶段的基础，但调度架构可能需要重构
3. **分层由理论决定**——不是拍脑袋，是约束的数学结构决定了版本边界
4. **每个阶段背负诚实声明**——偏差、条件保证、身份，从 v1 起不可省略

自行车→摩托车→轿车→跑车。

每一步都能上路，每一步都比上一步强，每一步都告诉你它做不到什么。
